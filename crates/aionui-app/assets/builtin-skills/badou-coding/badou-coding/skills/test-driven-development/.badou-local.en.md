## Toolchain (must read)

The historical constraints of this project (Badou framework / Spring
Boot 1.8 / Java 1.8) determine the TDD toolchain:

- **JUnit 4.12** (**not 5.x**). The framework's bundled
  `BaseHibernateDAOTest` and `JpaTemplateTest` use JUnit 4 APIs
  (`org.junit.Before` / `@Test` / `org.junit.runner.RunWith`).
  Migrating to 5 breaks the existing test base classes.
- **Mockito 1.10.19** (**not 2.x / 3.x**). 1.10.19 is the last
  version compatible with Java 1.8 + Spring. The framework's
  `bdPlugin-message` test stubs hard-code 1.x APIs (`Matchers`,
  `verifyZeroInteractions`).
- **Spring Test 4.x** (not 5.x) — ships with Spring Boot 1.8; do
  not manually upgrade.
- **AssertJ 1.x optional** — use it if already in the project; do
  not introduce it new.

## Test base classes (by layer)

| Test target | Must extend | Reason |
|---|---|---|
| DAO unit test | `com.badou.brms.base.test.BaseHibernateDAOTest` | Auto-injects Spring context + transaction rollback + field population |
| Service unit test | `com.badou.brms.base.test.BaseSpringServiceTest` | Same as above; auto-mocks same-package DAOs |
| Struts Action unit test | `com.badou.brms.base.test.BaseStrutsActionTest` | Handles Struts2 `ActionContext` initialization |
| Controller/Rest unit test | Use `MockMvc` + `@RunWith(SpringJUnit4ClassRunner.class)` yourself | No framework base class provided |
| Pure utility class | Plain JUnit 4 + Mockito 1.10.19 | — |

**Strictly forbidden** to `new` DAO/Service entities bypassing Spring
— the framework's `@Autowired` field population (creator, creation
time, etc.) depends on the Spring context.

## Naming and directory layout

- Test class name: `FooServiceTest` corresponds to `IFooService`;
  `FooDAOTest` corresponds to `IFooDAO`.
- Test method name: `shouldXxxWhenYyy` style (**not** `testXxx`),
  to enable IDE folding and report grouping.
- Directory mirror: `src/main/java/com/badou/project/foo/dao/IFooDAO.java`
  → `src/test/java/com/badou/project/foo/dao/FooDAOTest.java`
- One test method asserts one business scenario; split multiple
  scenarios into multiple `@Test` methods.

## Comments and Javadoc

- Javadoc on test methods **must be written in Chinese** (zh-CN),
  describing the business scenario, not what the code does. The
  reason: code reviewers in this org are not all English-fluent,
  and the test method's docstring is the primary review surface.
  Translate the business scenario into Chinese; do NOT write
  English summaries like "test the price = -1 case".
- Use full-width Chinese punctuation (，。、) in prose; use
  half-width punctuation in code identifiers.
- Complex test data: use `// given / when / then` three-part
  comments (**not** blank-line separators).

## Data and state

- For unit tests not depending on a database: switch the datasource
  in `applicationContext-test.xml` to H2 in-memory.
- When a real database is required: use the `init_framework` schema
  (development environment), **not** the production `init` schema.
- Cleanup strategy: in `@After`, call
  `BaseHibernateDAOTest#truncateAll()`; do not rely on Spring
  transaction rollback (rollback is unreliable in Flyway scenarios).
- Dictionary/enum data: use `comm_dictionary` fixtures; do not
  hardcode business IDs.

## Coverage and CI

- **Minimum 80% line coverage** (aligned with
  `~/.claude/rules/common/testing.md`).
- The `maven-surefire-plugin` in `pom.xml` is configured with
  `<skip>true</skip>`, so `mvn package` does not run tests.
- Run tests explicitly: `mvn test` or `mvn surefire:test`.
- CI must run:
  `mvn checkstyle:check && mvn test -Dmaven.test.failure.ignore=false`.
- Coverage report: `mvn jacoco:report` (if the JaCoCo plugin is
  configured).

## Do not

- **Do not** write "implement first, add tests later" commits; the
  TDD red-green-refactor order is mandatory.
- **Do not** use PowerMock to mock `static` / `final` (Mockito
  1.10 already supports this; resorting to PowerMock is a design
  problem — refactor instead).
- **Do not** test private methods (cover them indirectly via the
  public API).
- **Do not** use `Thread.sleep` in tests (use Awaitility 0.x
  instead).
- **Do not** use `@Ignore` / `@Disabled` to skip failing tests
  (fix the code, not the test).
- **Do not** comment out the test base class's `truncateAll()`
  "to save time" — it makes the next developer doubt the
  reliability of the entire test suite.

## Differences from the upstream superpowers rules

- superpowers:test-driven-development emphasizes the
  "RED-GREEN-REFACTOR" loop — **kept as-is**.
- superpowers suggests testing every line of implementation —
  **kept, but relaxed to 80% coverage** (framework legacy:
  some auto-generated setters/getters are not worth testing).
- superpowers suggests mocking all dependencies — **only at the
  Service/Controller layer**; the DAO layer uses a real database
  (H2/in-memory) (mocking JDBC hides SQL bugs).

## Test the Custom, Not the Generated

This project uses `backend-module-generator` to generate baseline CRUD and then customizes. Test responsibilities are split:

**DO test (custom code):**
- Custom service methods
- Custom validators
- Custom controllers (special URLs / parameters)
- Cross-table business logic

**DO NOT test (generator output):**
- Generated `md_module` / `md_field` / `md_form` records — covered by `idempotent_check.py`
- Generated `sys_resource` / `sys_role_resource` — same
- Generated DDL / CREATE TABLE SQL — same
- Generic CRUD interfaces of business tables (default `BaseSpringService` impls from the generator) — no need to test line by line

## Do not test generated entities

- **Do not** write unit tests for `FooEntity` (JPA entity auto-generated by the generator) — the generator guarantees it
- **Do not** test generated `getXxx()` / `setXxx()` — no value testing boilerplate
- **Do not** test whether `md_module` exists in the DB — that is `idempotent_check.py`'s job
- **Do not** test `comm_dictionary` data correctness — same

If you find "I must test the generated code" scenarios, the JSON definition is probably wrong — go back to `brainstorming` / `writing-plans` and check the field definitions.
