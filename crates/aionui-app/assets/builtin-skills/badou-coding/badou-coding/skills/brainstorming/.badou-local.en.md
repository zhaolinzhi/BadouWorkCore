## When to suggest using the generator

The generator applies to **any basic CRUD module** (employees,
orders, products, customers, dictionary maintenance, workflow
approvals, etc.) — it is not limited to any single business domain.
When the user describes a requirement with phrasing like the
following, **proactively suggest** going through the generator:

- "Build an XX management page" / "Add an XX module" / "Build an XX
  maintenance screen"
- "Add an XX to the admin backend"
- "CRUD" / "create-read-update-delete"
- "Like the products one" / "Same as XX"

## When NOT to use it

- **UI tweaks**: only changing the styles, copy, or field order of
  an existing module → edit the frontend directly.
- **Pure bug fixes**: bugs in an existing module → do not use the
  generator.
- **Non-MD systems**: CAS single sign-on, mobile uniapp, scheduled
  tasks → each uses its own dedicated tool or skill.
- **Data migration**: moving data from a legacy database to a new
  one → write a migration script.

## Scenario routing (post-decomposition)

During brainstorming, **ask the user first** which scenario applies:

1. **Pure CRUD (single-table or multi-table)**: business module only ->
   use `backend-module-generator`; read `rules/BASIC-CRUD.md` (+ `rules/MODULE-LINK.md` if relations).
2. **Pure flow (no business module)**: approval/workflow only ->
   use `backend-flow-engine`; read its `rules/FLOW-ENGINE.md`; produce `flow.json`.
3. **CRUD + flow**: **first** use `backend-flow-engine` to create `flw_flow`,
   **then** use `backend-module-generator` with `module.flow_code` set.
   Read `rules/FLOW-CONTRACT.md` for the integration contract.
4. **Post-generation customization**: overlay beyond standard CRUD ->
   `badou-md-customization-skill` (YAGNI, not yet built; document the boundary only).

**Do not pick for the user** - the flow scenario affects the `flow_code` setting and field conflicts.

## Output: a `module.json` draft

At the end of brainstorming, produce a `module.json` draft (or a
field list awaiting user confirmation). The draft must contain:

- `module.code` / `module.name_cn` / `module.db_table`
- a `fields` array (each field: `field_name` / `display_type` /
  `comment` / `length` / `nullable`)
- a `dictionaries` array (which fields use dropdowns)
- if a flow is included: `module.flow_code` +
  `module.flow_business_name_field`

Let the user review it, then hand it off to `writing-plans`.

## Handoff

Once the field list and the scenario are decided, **do not write
the JSON or run the generator inside the brainstorming phase** —
hand off to `writing-plans`. Reason: the generation steps belong
in the plan document (including re-run validation and the
customization phase), not in brainstorming's output.

## JSON field type mapping

Common mapping from business concepts to JSON field types:

| Business concept | `display_type` | Notes |
|---|---|---|
| Name / title / code | `varchar` | `length: 100` |
| Description / remark / long text | `text` | no `length` |
| Integer (quantity, age) | `int` | |
| Amount / ratio | `decimal` | pair with `length: 18, scale: 2` |
| Date (no time component) | `date` | |
| Timestamp | `datetime` | |
| Boolean (yes/no) | `tinyint` | `length: 1` |
| Hidden field | `hidden` | for system fields like creator / creation time |
| Read-only field | `readonly` | for fields back-filled from external systems |

## Do not

- **Do not** write SQL files yourself — that is the generator's job.
- **Do not** skip the generator and hand-write table DDL "for
  speed" — the next re-run will overwrite it.
- **Do not** add `approval_status` / `audit_status` / `status`
  fields yourself — when `flow_code` is non-empty, the generator
  auto-injects `BO_STATUS`; defining your own will conflict.
- **Do not** decide "does it include a flow?" on the user's behalf
  — that business judgment must be confirmed by the user.

## Differences from the upstream superpowers rules

superpowers' `brainstorming` produces a "feature spec + user
stories"; our brainstorming additionally produces a
"`module.json` field draft" (CN field names + types + lengths) so
the downstream `writing-plans` step can use it directly.

- Cross-stack spec → workspace root `docs/badoucoding/specs/`

## Cross-stack automation awareness

When the working directory is `badou-workspace/` with `backend/`, `frontend/`, `.claude/` siblings (the target layout of this design), **append Q5** after the original 4-scenario routing:

> Q5: Does this module need frontend customSetting?
> - No → standard CRUD + flow generation
> - List customization → call `frontend-module-list`
> - Edit customization → call `frontend-module-edit`
> - Tree customization → call `frontend-module-tree-{edit,list,table}`
> - Field extension → call `frontend-module-extend-field`

**Output extension** (cross-stack scenario):
- `module.json` (existing)
- `flow.json` (existing, if flow included)
- `contracts/<mdCode>/backend-api.yaml` (**new**)
- `contracts/<mdCode>/frontend-js.yaml` (**new**, if frontend customization needed)

**Trigger condition**: `pwd` contains `backend/`, `frontend/`, `.claude/` as siblings. Does NOT trigger in single-repo contexts (e.g. `initial-project/`).
