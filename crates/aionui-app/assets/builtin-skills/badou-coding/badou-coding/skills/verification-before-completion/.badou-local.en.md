## Three-step gate

Any module that includes `backend-module-generator` **must** run
these 3 steps before declaring "done"; every exit code must be 0:

```bash
# 1. Generator exit code 0
python3 .claude/skills/backend-module-generator/crud_generator.py \
    --def <module>.json --output ./output
# Expected: exit 0 + output "✅ Sync complete"

# 2. SQL executor exit code 0
python3 .claude/skills/backend-module-generator/db_executor.py \
    output/<module>/v<ver>/<module>_create.sql \
    --config-from-brain .trellis/PROJECT-BRAIN.md
# Expected: exit 0

# 3. Validator exit code 0 + ALL PASSED
python3 .claude/skills/backend-module-generator/validators/idempotent_check.py \
    <module>.json
# Expected: exit 0 + final line "ALL PASSED ✅"
```

**Any non-zero exit code = not done.**

## What `idempotent_check` verifies

8 categories of checks:

1. **Model designer**: `md_module` exists; name / table name correct;
   `flow_id` link present when applicable.
2. **Field completeness**: every JSON field exists in `md_field` with
   matching type.
3. **Form reasonableness**: `dict` → select dropdown, `date` → date
   picker, `text` → textarea, `decimal` → number + validation.
4. **Dictionary data**: dictionary type exists, dictionary item count
   correct, names match.
5. **Menu / permissions**: menu exists, all 6 standard button resources
   present, role authorization wired.
6. **Flow engine** (when `flow_code` is set): `busi` / `flw_flow` /
   `flw_node` / `flw_route` / `comm_handler` counts are consistent and
   links are complete.
7. **DDL completeness**: business table exists with the four required
   fields `id` / `create_time` / `update_time` / `flg_deleted`.
8. **Idempotent safety**: safe to clean up and rebuild repeatedly
   without affecting other modules.

## Exit codes

- **0 = pass**: may declare done.
- **1 = fail**: must fix and re-run the entire pipeline (not just the
  validator).

## Handling failures

When `idempotent_check.py` fails:

1. Look at which category failed (output marks it with ❌).
2. Fix the corresponding JSON / data.
3. **Re-run all 3 steps** (not just the validator) — the SQL may need
   to be regenerated and re-executed.
4. Repeat until `ALL PASSED`.

Re-running only the validator = pretending to pass = the data is not
actually fixed.

## Re-run safety

All 3 steps are idempotent: you can re-run the same module N times.
`crud_generator.py` first runs `rm -rf` + `cp -R` (generator artifacts
are rebuildable); `db_executor.py` uses `INSERT` mode and
`idempotent_check.py` verifies the data already exists; the validator
itself has no side effects.

**Prerequisite**: you must use `db_executor.py` (not bare `mysql`) —
bare `mysql` may fail parts of the SQL on re-run because session
variables get lost.

## CI integration

Recommended pipeline (when the project has CI):

```bash
mvn checkstyle:check \
  && python3 .claude/skills/backend-module-generator/crud_generator.py --def module.json --output ./output \
  && python3 .claude/skills/backend-module-generator/db_executor.py output/<module>/v<ver>/<module>_create.sql --config-from-brain .trellis/PROJECT-BRAIN.md \
  && python3 .claude/skills/backend-module-generator/validators/idempotent_check.py module.json
```

**The order cannot be changed** — static check (checkstyle) first,
then generate, then execute, then verify.

## Do not

- **Do not** skip `idempotent_check.py` — skipped modules have a 100%
  failure rate (dictionary three-conditions, flow field conflicts,
  etc.).
- **Do not** declare done when the output "ALL PASSED" is missing.
- **Do not** modify generated SQL and skip re-running the validator —
  changed SQL = divergence from the JSON definition; the next re-run
  overwrites it.
- **Do not** treat "validator failure" as a "known issue" to leave
  behind for someone else — fix it on the spot.
- **Do not** run only the validator without the generator and
  executor — all three must run together.

## Differences from upstream superpowers

The superpowers verification is "tests pass + lint clean"; our
verification additionally requires `idempotent_check.py` to output
`ALL PASSED`, covering 8 categories of generator-specific checks.
