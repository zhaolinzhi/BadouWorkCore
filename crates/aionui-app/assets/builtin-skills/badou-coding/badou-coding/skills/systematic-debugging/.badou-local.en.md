## Dictionary dropdown is blank

**Symptom**: the frontend dropdown is empty even though the
`comm_dictionary` table holds data.

**All 3 conditions are required**:

1. The field has a `dict` attribute (e.g. `"dict": "GENDER"`).
2. The JSON top-level declares a `dictionaries` array (with
   `"type": "GENDER"` plus `"items": [...]`).
3. The field's `form.edit_type` is `"select"`.

If any one is missing the generator will not create the dictionary
relation and the dropdown stays blank.

**How to debug**: open the generated `md_field` row and check whether
the `DICT_TYPE` column is non-empty.

## flow_code field conflict

**Symptom**: running `crud_generator.py --def module.json` raises a
Pydantic validation error (e.g. "approval_status field type
mismatch").

**Cause**: when `module.flow_code` is non-empty, the generator
**automatically injects 7 workflow fields** into the business table
(including `BO_STATUS`). If `module.json` also defines fields like
`approval_status` / `audit_status` / `status`, they collide with
`BO_STATUS`.

**Fix**: remove every "approval / audit / status" field from
`module.json` — the `BO_STATUS` dictionary (Draft / Approving /
Approved / Rejected) is maintained automatically by the generator.

## flow_code processor_value

**Symptom**: running `--flow-only flow.json --flow-execute` makes
Pydantic complain "value third segment error".

**Cause**: an abstract handler (`type=1`) uses a `value` shaped like
`"1!@!drafter/submitter!@!<comm_handler_rule.ID>"`. The third
segment **must** be the real ID from the `comm_handler_rule` table,
**not** `0`.

**Fix example**:

```json
// WRONG
{"type": 1, "value": "1!@!drafter/submitter!@!0"}

// RIGHT (drafter/submitter = comm_handler_rule.ID 3)
{"type": 1, "value": "1!@!drafter/submitter!@!3"}
```

## Cleanup ordering

**Symptom**: re-running `crud_generator.py` triggers an `INSERT`
conflict (duplicate primary key).

**Cause**: `cleanup.sql` deletes in reverse-dependency order.
Re-running without cleanup first leaves stale rows behind.

**Fix**: before every re-run, **first** execute `cleanup.sql`:

```bash
python3 .claude/skills/backend-module-generator/db_executor.py \
    output/<module>/v<ver>/<module>_cleanup.sql \
    --config-from-brain .trellis/PROJECT-BRAIN.md
```

Or rely on `idempotent_check.py` to auto-cleanup before generation
(default behavior).

## Cross-project DB bleed

**Symptom**: after running the generator, the writes land in
another project's database.

**Cause**: `<project>/.trellis/PROJECT-BRAIN.md` is per-project
config; each project has a different path.

**Fix**: before every generator run, **first confirm** that the
PROJECT-BRAIN.md path is correct for the project you're in — do not
copy-paste a command from a previous run.

## Must use db_executor

**Symptom**: running `mysql < create.sql` causes some statements to
fail ("Unknown column" or "Variable not set").

**Cause**: the generated SQL uses many MySQL user variables
(`@module_id` / `@field_xxx` / `@menu_resource_id`) that depend on
the **same connection's session context**. The bare `mysql` CLI may
switch connections per execution and lose those variables.

**Fix**: use `db_executor.py` (internally uses a state machine to
split on `;`, a single PyMySQL connection, `autocommit=False`, and
failure rollback).

## Do not

- **Do not** hand-edit SQL under `output/` to "fix it" — changing the
  JSON and re-running will overwrite your edits.
- **Do not** assume idempotency without verification — you must run
  `idempotent_check.py` to confirm.
- **Do not** write `0` for an abstract handler — look up the real ID
  in the `comm_handler_rule` table.
- **Do not** run generated SQL through bare `mysql <` — use
  `db_executor.py`.

## Differences from superpowers

Superpowers debugging is generic (any stack); our debugging focuses
on the 6 known failure patterns produced by the generator
(dictionary / field conflict / processor_value / cleanup / cross-
project bleed / db_executor).
