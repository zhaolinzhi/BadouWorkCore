## Do not run generators in parallel

**Do not** run these in two sub-agents in parallel:
- `crud_generator.py --def A.json`
- `crud_generator.py --def B.json`

**Why**: the SQL produced by `crud_generator.py` relies heavily on MySQL user variables (`@module_id` / `@field_xxx` / `@menu_resource_id`), which depend on a **single connection's session context**. When run in parallel, each sub-agent's connection maintains its own variable set, so the second agent's `@module_id` may be a leftover from the first agent — **silent data corruption** (no error, but records get crossed).

## Scenarios where parallel is OK

| Scenario | Parallel OK? | Why |
|---|---|---|
| Cross-project (different DB / different `PROJECT-BRAIN.md`) | ✅ | No mutual effect |
| Preparation phase (writing multiple `module.json` files) | ✅ | Pure file I/O |
| Post-generation customization (one sub-agent writes one service layer) | ✅ | Does not run the generator |
| Same DB with multiple generators | ❌ | The variable conflicts above |

## Safe mode

When you need to batch-generate N modules against the same DB:

```python
# single sub-agent serial loop
for json_path in module_jsons:
    subprocess.run([
        "python3", "crud_generator.py",
        "--def", json_path,
        "--output", "./output"
    ], check=True)
    subprocess.run([
        "python3", "idempotent_check.py", json_path
    ], check=True)
```

**Do not** use `subprocess.Popen` for concurrency; use `subprocess.run` serially.
