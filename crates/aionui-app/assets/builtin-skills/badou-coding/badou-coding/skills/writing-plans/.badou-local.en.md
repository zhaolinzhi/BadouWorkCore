## Plan structure (5 steps)

Every implementation plan for a new module (including CRUD) must
follow these 5 steps:

| Step | Activity | Output |
|---|---|---|
| 1. Confirm requirements | Field list + scenario (single-table / multi-table / flow) | Reviewed `module.json` |
| 2. Run the generator | `crud_generator.py --def <json>` | `output/<module>/v<ver>/*.sql` |
| 3. Execute SQL | `db_executor.py <create.sql>` | Module exists in DB |
| 4. Verify | `idempotent_check.py <json>` exit code 0 + "ALL PASSED" | Verification passed |
| 5. Customize | Write service / controller / validator | Business feature usable |

**Steps 1-4 cannot be merged.** **Step 5 is the TDD phase.**

## Generation step details

When written into the plan, Step 2 must include:

- **Command**: `crud_generator.py --def <absolute-path> --output <absolute-path>`
- **Input JSON path**: `<project>/crud-generator/module_defs/<module>.json`
- **Output verification**: the plan must say "check that the output directory contains three files: `create.sql` + `cleanup.sql` + `manifest.json`"
- **Failure rollback**: if the generator exits with non-zero, do not proceed to Step 3 — first check the JSON validation error

## Flow engine variant

If `module.flow_code` is non-empty:

1. **First** write `flow.json` (flow definition: `busi` + `nodes` + `routes`)
2. `crud_generator.py --flow-only flow.json --flow-execute` to create the 5 flow tables
3. **Then** write `module.json` (reference the flow above via `module.flow_code`)
4. `crud_generator.py --def module.json` to create the business module
5. `db_executor.py` + `idempotent_check.py`

**Reversing the order = the `flow_id` link breaks** (the `UPDATE md_module SET flow_id` subquery inside `create.sql` cannot find `flw_flow`).

## Multi-project variant

Add one item to Step 1:

- Confirm `<project>/.trellis/PROJECT-BRAIN.md` exists
- Confirm the DB connection info is filled in (`host` / `port` / `db` / `user` / `password`)
- Do not assume the DB — read `PROJECT-BRAIN.md`

## Customization phase

Step 5 must specify the customization scope (do not let the plan say "just finish it"):

- Custom service methods (business logic, cross-table operations)
- Custom controller (special URL, special parameters)
- Custom validator (cross-field validation, remote validation)
- Custom frontend (when `md_field` + `md_form` are not enough)

Each customization item must have a "corresponding test case" link pointing to the TDD phase.

## Idempotency

The plan must state explicitly: **every generation step can be re-run.** If Step 4 fails, fix the JSON and re-run Steps 2-4 — do not edit the SQL manually.

CI integration (when the project is configured):

```bash
mvn checkstyle:check \
  && python3 .claude/skills/backend-module-generator/validators/idempotent_check.py module.json \
  && mvn test
```

## Do not

- **Do not** put "modify the generated SQL" in the plan — editing it bypasses the generator and the next re-run will overwrite your changes.
- **Do not** skip Step 4 verification — `idempotent_check.py` checks 8 categories of issues; skipping it will cause production bugs.
- **Do not** run generation plans for multiple modules against the same DB in parallel — MySQL user-variable conflicts will corrupt the data.
- **Do not** use bare `mysql < create.sql` "for speed" — must use `db_executor.py` (preserves session variables).

## Differences from the upstream superpowers rules

The superpowers plan stops at "begin implementation"; our plan **explicitly includes the generation phase** (Steps 2-4) — generate model data first, then write custom code on top.

## Output location override

Do not use the upstream default `docs/superpowers/plans/`. **All plan output goes to workspace root `docs/badoucoding/plans/`** (plain folder, not git-tracked; for cross-team reference).

- Cross-stack plan → workspace root `docs/badoucoding/plans/`
- Single-stack plan → workspace root `docs/badoucoding/plans/` (also written to root; no per-repo split)

`.claude/docs/` is reserved for frontend/backend reference docs and general documentation only; **do not** put plan there.

## Task scope labeling

Each plan task labels its `scope` so subagent-driven-development knows which directory to `cd` into:

| scope | meaning | task runtime cwd |
|---|---|---|
| `backend` | backend only | `backend/` |
| `frontend` | frontend only | `frontend/` |
| `cross-stack` | cross-stack | current workspace root (`badou-workspace/`) |
| `framework` | third repo | `.claude/` |

**Task template**:

```markdown
### Task N: <title>
- scope: backend | frontend | cross-stack | framework
- cwd: backend/ | frontend/ | .claude/ | .
- skill: <skill-name>
- inputs:
  - contracts/<mdCode>/<contract-file>.yaml
  - <other inputs>
- outputs:
  - <expected outputs>
- validation:
  - <how to verify>
```

subagent-driven-development subagent behavior: `cd <task.scope directory>` on entry, do not cross scope; `scope=cross-stack` tasks are executed by the main agent, not dispatched to subagents.
